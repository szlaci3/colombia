# Formlane architecture

## Native voice Dialog

The separate [native Dialog](dialog.md) uses `gemini-3.8-live` audio-to-audio over a browser-to-Google WebSocket. A same-origin server function issues a short-lived single-use token with the complete setup locked; the permanent key stays server-side. `server/voice-context.ts` reads the product guide packaged with the voice function and includes it directly in the constrained system instructions. This gives product knowledge without retrieval or access to the open project. AudioWorklet capture, PCM encoding/playback, binary protocol handling, interruption, and transcript grouping live in the `src/voice*` modules. App retains chronological transcript messages in memory when the dialog closes; they never enter project storage or exports. Dialog has no application tools and does not replace the reviewed proposal assistant. Talker's working Dialog was inspected read-only as a reference.

## State and rendering

React and TypeScript render a single versioned JSON project. `src/model.ts` defines six discriminated block types and six independently editable page arrays: webshop, Kanban, data table, blog, social feed, and dashboard. All pages reference the same project-level brand/theme. `src/components/Blocks.tsx` renders the same data in editing and presentation modes, so preview does not have a second implementation to drift out of sync.

Themes use an allowlisted preset or optional validated custom palette, font category, and numeric radius, passed to the canvas as CSS custom properties. Custom palettes contain only six-digit hex colors and bounded source metadata; arbitrary CSS is never accepted. Existing v1 projects remain compatible. The application chrome stays consistent while every prototype changes together. Original SVG illustrations are React components, so they work offline and scale without asset hosting.

`historyReducer` records immutable project snapshots and caps history at 50 steps. A change after undo discards the redo branch. Navigation, selection, dialogs, and viewport width are editor state, not project content. Text commits on blur rather than recording a snapshot per keystroke. Escape restores the previous value. Native text undo remains available while a field has focus.

The editor uses ordered blocks rather than arbitrary pixel positioning. Responsive sections provide useful meeting-time rearranging without creating a full design tool. Each page uses a query parameter, which works on static hosts without server rewrites.

## Template composition and v1 compatibility

The new templates compose existing hero, text, and table blocks. An optional allowlisted text `appearance` selects plain text, article, post, or metric presentation. Article/post variants use semantic articles; post initials derive from the editable title; metric bodies use a first line for the figure and subsequent lines for its caption. These remain ordinary bounded strings, not analytics or a new data primitive. “Section style” changes the variant in one history transaction and is hidden during presentation. Duplication, content import, file/snapshot export, and undo use the same block model.

`createTemplate` supplies fresh IDs for the blog, social, and dashboard starters. The v1 schema retains its three required original pages; missing new pages receive validated starter data through schema defaults. Explicitly supplied malformed/empty new pages still fail validation. Existing content, IDs, shared theme, and provenance are preserved. Once normalized, all six arrays are serialized, so subsequent loads retain their IDs and edits. Old local saves, JSON files, and compressed snapshot links use the same path. Project files remain v1; the workspace catalog stores validated v1 snapshots.

The 750 KB limit is checked both before parsing and after adding starter pages. A legacy save too close to the limit is protected by the existing recovery flow rather than autosaving an unreadable expanded project. Users can reduce an exported legacy file and reimport it. The checked-in three-page fixture exercises all three entry points. Global ID, table-shape, content, and appearance validation covers every template.

`src/templates.css` provides variant and template styling through the shared palette/font/radius variables. Dashboard metrics use a responsive grid and `rectSortingStrategy`; other sections use the existing vertical strategy. Native source order remains the reading and persisted order. Controls stay available at narrow widths, metric cards stack, and table overflow stays inside its named scroll region. Six-template navigation is shared by the sidebar, prototype header, URL query, and presentation selector.

## Rearranging and accessibility

`@dnd-kit/core` and `@dnd-kit/sortable` provide pointer and keyboard dragging. Sections and Kanban cards have separate contexts, with dedicated handles to avoid interfering with inline editing. Kanban supports same-column ordering and movement between columns, including empty ones. Section arrows, product arrows, and card destination menus provide alternatives to dragging.

Native dialogs provide focus containment and Escape dismissal. Inputs and editing controls have accessible names. Browser tests run axe checks on every template and the introduction dialog. These automated checks supplement keyboard tests; they do not establish complete assistive-technology compatibility.

`useNavigationDrawer` contains keyboard focus in the phone navigation, makes the workspace inert, and locks background scrolling. Closing restores the navigation trigger; resizing to desktop releases the drawer. Tools close the drawer before opening a native dialog. Dialog backdrop dismissal requires both pointer-down and click outside the dialog bounds, preserving work when a drag starts inside. Inline editing and global shortcuts ignore active input-method composition.

`IntroductionVideo` uses native playback controls and metadata preloading. Media errors expose a retry and retain the download link; successful metadata loading clears the error. Opening the introduction never changes project data.

## Persistence and sharing

`src/storage.ts` owns project-file validation, legacy serialization, and compressed URL snapshots. Zod validates imports and stored data, including duplicate nested IDs, bounds, and table shape. Invalid imports leave the current project intact. Corrupt saved projects open a recoverable unsaved draft and pause autosave. Storage failures stay visible, and file export continues to work.

`src/workspace.ts` stores the device-local library in one versioned `formlane.library.v1` value. Its entries have stable IDs, revision counters, timestamps, complete project drafts, and up to 10 named checkpoint snapshots. The catalog supports 10 projects and 3 MB of UTF-8 JSON; each draft/version also passes the existing 750 KB project parser. Limits and browser quota failures never evict older data. A successful single-key write commits the library; a best-effort `formlane.project.v1` compatibility cache follows it. Existing single-project saves migrate on the first successful save. The library is authoritative after migration.

Autosave is debounced, with page-hide and visibility-change flushing. Project switches and duplication flush the current draft before opening another project. Unchanged data does not introduce a new revision. Saves reread the library, merge other entries, and compare the current entry's revision before writing; an observed stale tab must export/reload rather than overwrite a newer save. This is optimistic detection, not a cross-tab transaction or live synchronization: simultaneous read/write races are still possible with local storage. Use one editing tab per project. Autosave in an older tab does not change the library's selected-project pointer. Reload restores content but not session undo; opening another project resets that stack. Checkpoint restoration uses one ordinary history change and can be undone.

Invalid libraries open a protected draft without overwriting the original. Explicit “Save this draft” first writes the exact unreadable library to a separate `formlane.library.recovery.*` key, then initializes a new library; a failed backup leaves the original untouched. Project and version removal are confirmed, and the active project cannot be removed. File/snapshot exports remain single-project v1 documents without library metadata or version history; each checkpoint can be exported separately.

Sharing uses `lz-string` in the URL fragment, with the current template in the query. Fragments are not part of HTTP requests, but anyone receiving the URL receives the project data. There is no server upload, live sync, permission model, link revocation, or guarantee that other applications preserve long links. Opening a shared project pauses autosave until an explicit “Keep this copy”, which adds a new library entry while preserving existing projects. JSON export is the reliable fallback for large projects.

Generated snapshot links remove the introduction query parameter so recipients reach the shared prototype directly.

## PDF handouts

`PdfPreview` renders the same `BlockContent` components as the editor in read-only mode, with the shared theme and a current/all-template selector. Read-only text preserves line breaks, including metric figures and captions. The preview waits for bundled fonts before invoking native printing; there is no PDF service or raster screenshot library. The browser's Save as PDF produces selectable text and vector SVG art. A print stylesheet supplies A4 portrait pages, template breaks, repeated table headers, wrapping wide cells, and unclipped board columns. Long documents may span additional pages; print settings and pagination remain browser-dependent. PDF is a static handout, and JSON remains the editable export. Automated Chromium tests generate real PDFs; development checks additionally extract PDF text and visually inspect rendered pages.

## Website style import

`netlify/functions/import-style.mts` handles same-origin JSON POST requests at `/api/import-style`. It uses `server/public-fetch.ts` for bounded outbound requests, `server/style-cascade.ts` for a bounded static author-style sample, and `server/extract-style.ts` for ranking/adaptation. Cheerio matches selectors to representative page/heading/action elements and their ancestors. PostCSS reads embedded and linked styles in document order; linked sheets retain their original URL identity even when other fetches fail. The `specificity` parser compares selector specificity, including `:is()`/`:where()`. Applicable declarations resolve by importance, inline priority, specificity, and order. Inline declarations remain attached to their original element. Background shorthand and color longhand share a cascade slot; this is not general shorthand expansion.

Custom-property names remain case-sensitive. Values resolve within each sampled element’s inherited scope, including nested function fallbacks, cycles, and values computed at an ancestor before inheritance. Expansion depth/size is bounded. Explicit hidden elements and sampled `display:none`/`visibility:hidden` content do not contribute observations. Conditional rules, interactive selectors, pseudo-elements, layers, nesting, and animations are omitted with notes. Only unconditional `all`/`screen` media are accepted. This deliberately omits CSS features requiring a browser environment; it is not a computed-style engine. Limits bound analysis to 120 elements, 2,000 rules/selectors, and 25,000 declaration applications. Font shorthand, registered properties, full CSS-wide keyword semantics, relative-unit computation, and advanced background expansion remain unsupported.

Color.js normalizes supported colors, including OKLCH. Heuristics rank winning declarations using element/property roles, with global theme tokens and metadata as additional evidence. Source evidence identifies the selected value, selector, property, stylesheet label, and basis (matched, token, metadata, or fallback) for accent, page, text, font, and radius. The response schema bounds these strings; the UI renders them as text only. `StyleEvidence` compares unchanged detected values with the current review choices, so color picking or manual edits never rewrite source evidence. Evidence is review-only and does not change the project format. Existing responses without evidence remain supported. The importer does not execute source scripts, copy source markup into the editor, follow CSS imports, or download fonts/images.

Every request resolves all addresses and rejects the target if any is nonpublic. The HTTPS transport connects to the selected vetted address using a custom lookup while retaining the original hostname for TLS verification. Redirects repeat the validation, preventing a public URL from redirecting to a private target. Only HTTPS on port 443 is accepted, without credentials or IP-literal hosts. Outbound requests forward no cookies, authorization, or user headers. Limits bound response bytes, stylesheet count, redirects, DNS time, and total analysis time. Netlify provides a per-IP/domain limit of 10 imports per minute; the local Vite adapter does not emulate platform rate limiting.

The review dialog displays observed colors separately from the proposed palette, documents substitutions, supports manual corrections, and gates application on contrast. Bright accents are darkened and dark backgrounds are adapted to the light template system. Source fonts map to bundled/system serif or sans fallbacks rather than being downloaded or implying license rights. Applying a result updates the shared theme in one history transaction; optional brand renaming is part of that same transaction. Existing content is preserved. Cancelling, closing, and failed requests leave the project unchanged; an unmounted review aborts pending work.

`server/vite-api.ts` runs the same handlers during local dev and preview. The browser build includes no Node-only fetching or parsing dependencies. Netlify deploys the frontend and functions together. TypeScript 5.9 provides the compiler API needed by Netlify tooling. Mocked browser flows and parser/security unit tests supplement actual hosted function checks.

## Webpage content and Markdown

`netlify/functions/import-content.mts` exposes `/api/import-content`. Both import functions use `server/url-import-handler.ts` for method/origin/JSON validation, bounded request bodies, timeout signals, and safe errors, then the same DNS-pinned public HTTPS fetcher. Content import fetches a single page and never follows source links or media. Each function has its own platform rate limit of 10 requests per minute per IP/domain.

`server/extract-content.ts` cleans the document with Cheerio, preferring `main`, then `article`, then `body`. It removes active markup, known navigation and forms, and explicit hidden elements. It normalizes links to allowlisted HTTP/HTTPS/mail addresses and replaces images with escaped alt text. Turndown produces Markdown with a bounded table rule; literal angle brackets in ordinary text are escaped. No source scripts execute, and the UI displays Markdown in a read-only textarea rather than rendering HTML. CSS-based visibility and client-rendered content are not evaluated.

Headings group plain text into existing text blocks, and tables map to existing editable table blocks. No new editor primitive or project-version migration is needed. The adapter offers up to 20 sections with 2,000-character text bodies and rectangular tables bounded to 20 columns/100 data rows. Merged cells and missing headers receive explicit adaptation notes. The Markdown export includes source provenance and retains supported headings, lists, links, code, quotes, and tables; it can include content beyond the 20 editable sections but is limited to 100,000 characters. Long table cells are shortened only in the prototype. The complete source HTML is not returned or saved.

`WebsiteImport` presents visual-style and page-content modes in the same dialog. `ContentImport` handles selection, inert Markdown review, clipboard fallback, and a real `.md` download. `appendImportedSections` clones chosen sections with fresh IDs, inserts them after the selected section or at the end, and enforces page capacity. Applying them goes through one project-history transaction and retains other pages and the shared theme. Full pages can still export Markdown. Cancel, failure, and mode switching do not change project content. The original page under `public/examples/studio-notes.html` supports a repeatable first-party demonstration and opt-in hosted end-to-end checks.

## Local Markdown and content selection

`src/markdown-import.ts` is a browser-only adapter loaded with a dynamic import when the user prepares pasted Markdown. Marked supplies tokens, never rendered HTML. The adapter walks them into plain editor data; `entities` decodes text character references without creating DOM nodes. Code remains literal, link targets are never followed, and images contribute alt text only. Raw HTML blocks/tags are omitted from sections, with notes; the complete original Markdown remains inert text for review/copy/download. No pasted text is posted to an API, and no source URL is invented.

The adapter validates 100,000-character input, 20 offered sections, 2,000-character text/cells, and rectangular 20-column/100-row tables. Text chunks avoid splitting Unicode surrogate pairs. Nested token traversal is bounded to 40 levels and 30,000 visits; lexer failures and unsupported/empty documents return a useful error. Tables nested inside lists/quotes flatten to plain text. Overflow adaptations are reported, while export retains the original document unchanged. `markdownImportSchema` shares section-shape and ID checks with the website result through `safeExtend`; `contentImportSchema` still requires a public HTTPS source and cannot accept a local review result. The project schema and version stay unchanged.

`ContentImport` owns source choice, temporary pasted text/title, result, selected IDs, cancellation, and export. Switching input types aborts pending requests and discards the review while retaining inputs for the dialog session. Editing the source invalidates its review. A late request or lazy-module result cannot replace a cancelled review. Closing the content mode discards temporary inputs/results; only explicitly applied sections reach autosave. The lightweight meeting example is separate from the lazy parser chunk.

`ContentSections` is shared by website and local Markdown reviews. Search covers titles, bodies, headers, and cells; type filters never deselect hidden choices. Counts identify selections outside the filter. Bulk selection adds matching sections only up to remaining capacity and retains existing selections. Chosen IDs are filtered through the original source array on application, retaining source order. Full previews render text as React strings; tables have named keyboard-scrollable containers. Selection/filtering/preview are review state, so they do not create project history entries.

## Reviewed assistant suggestions

`src/assistant.ts` defines strict, allowlisted proposal operations: shared brand/theme, section text, text additions, section movement/removal, table headers/cells, and appended table rows. There are no arbitrary object paths, code, remote URLs, or execution tools. `reviewProposal` applies operations to an isolated clone, checks target IDs/types/fields and structural limits, generates new IDs locally, then passes the complete project through the existing schema and 750 KB parser. Any invalid operation rejects the whole proposal. Review captures a base-project serialization and the exact validated next snapshot. Apply checks the current project still matches that base and dispatches one history change. Other projects, library metadata, and saved versions remain outside this contract.

`Assistant` lets the user share the current template or any of its sections directly from the dialog. Numbered section options use their current headings; an editor selection is preselected on opening. Section values use a `section:` prefix to distinguish IDs from the whole-template choice. Only the chosen section reaches the context; if a project change removes it, the control and context both fall back to the current template while invalidating the previous proposal. The request includes project name, shared brand/palette/font/radius, and only those sections; imported palette provenance and other templates/versions are omitted. Context cloning is memoized while the prompt changes. Before/proposed values and model summaries render as inert React text. Closing, editing the prompt/context, cancelling, or changing the project aborts/discards pending work; a request identity check prevents late responses from restoring stale reviews. Advice-only responses have no Apply action. Requests and proposals stay in dialog memory and are not persisted. The clearly labeled built-in example uses the same review/apply engine without posting content or claiming an AI response. Dialog cleanup restores keyboard focus to the opener.

`netlify/functions/assistant.mts` exposes `/api/assistant`: GET returns availability only; POST requires same-origin JSON and bounded, validated input. Both an explicit server activation flag and API key are required. `server/assistant.ts` calls the fixed Google Interactions endpoint with `store:false`, Gemini 3.5 Flash-Lite by default, bounded output, and a 50-second signal. The browser deadline is 55 seconds, below the platform limit of 60 seconds. The live API rejected the original complete operation schema. The accepted wire schema derives a shallow operation object from the shared union: an operation-type enum, optional typed fields, nullable type arrays, and per-operation required-field guidance. It omits wire counting/numeric/string constraints and additional-property restrictions. Full operation-specific required fields, extra-field rejection, limits, and semantics remain enforced by the original strict Zod schema on both server and client. Context is supplied as data under separate fixed instructions. No provider tools are enabled. Only completed interaction envelopes with model-output text are accepted; thoughts are ignored and refusals, incomplete results, tool steps, malformed output, proposal shape, and operation semantics are validated before anything is returned. Provider errors are sanitized rather than relaying credentials or account details. The client independently validates the proposal against the actual current project before offering Apply.

The endpoint limits input to 65 KB, prompts to 2,000 characters, provider responses to 150 KB, and proposals to 12 operations. Netlify limits the function to six requests/minute/IP/domain, including GET checks. This is a public, bounded endpoint when enabled, not authentication or a global spending cap. Provider project usage controls remain necessary for an operator enabling a public demo. Cancellation prevents stale application but cannot promise to cancel provider billing. The local Vite middleware reads only the named server configuration from environment/`.env.local` and never exposes the provider key through `VITE_` settings. See the README's setup, rollback, and opt-in live check. Ordinary tests use controlled provider responses. Real Flash-Lite brand, selected-hero, and table-header proposals were verified locally on 2026-10-21. The opt-in hosted generation/review/apply/undo check passed after deploying `afe8fa5`, and the user confirmed the production manual test passed. Server model overrides remain explicit and no fallback model is silently invoked.

The reviewed assistant includes the Interactions/Flash-Lite production-timeout repair; see the README for diagnostic evidence and the opt-in deployment check. The introduction video is available; the separate polished guided example remains pending. A static-only host can serve the editor/example, but needs compatible endpoints for URL imports and AI suggestions.
